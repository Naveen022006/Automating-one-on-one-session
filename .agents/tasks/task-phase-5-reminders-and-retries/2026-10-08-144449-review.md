# Reschedule/cancel robustness and the reminder fire-time backstop (v2)

The fix commit (3007ca8) reworks the reschedule ordering and the reminder run-time guard to close the five behavioral gaps v1 raised, and re-states the sixth (unauthenticated routes) as a documented Phase-6 deferral. Reminders now carry the start time they were enqueued for and skip at send time when it no longer matches the booking's current session, so the "only the new reminders" guarantee no longer rests solely on `cancelReminders` succeeding. `enqueueReminders` does remove-then-add so a stale delayed job is really replaced, and reschedule now replaces reminders *before* the fallible Calendar patch so a mid-flow failure leaves a re-drivable state rather than a reminderless booking. The cancellation message send is wrapped so a provider outage can no longer abort a cancel.

Watch for: the new ordering enqueues the new-time reminders before the Calendar event is patched, so a 15m reminder could in principle fire before the invite is moved — but the reminder body reads `session.startTime` (already committed to the new time) and the booking stays SCHEDULED, so the customer gets a correct message and only the calendar invite lags until the patch is re-driven (confirmed, acceptable). The two mutation routes remain unauthenticated by design (confirmed, deferred to Phase 6).

**Verdict**: APPROVED

## High-level view

Issue 1 (fire-time backstop) is fully closed. `enqueueReminders` writes `expectedStartTime` (ISO) into each job, the worker threads it into `sendReminderForBooking`, and that function skips when the expected time no longer equals the current `session.startTime`. A reschedule leaves the booking SCHEDULED, so this time comparison — not the status check — is what makes a surviving stale job for the old slot a no-op.

Issue 2 (reschedule atomicity) is addressed by reordering, not by a transaction. Reminders are replaced immediately after the session move commits and before the Calendar patch and message send, so a throw in those later steps can no longer leave a SCHEDULED booking with zero reminders. `enqueueReminders` now removes any existing job before adding, so the replace isn't swallowed as a BullMQ duplicate-id no-op.

Issues 2/4 interact on recoverability: because the session move has committed and reminders already point at the new time before `updateEvent` runs, a transient Calendar failure records `lastError`, surfaces as 409, and leaves a state that re-running the same reschedule simply re-patches (the session move is idempotent, the deterministic ids make the reminder replace idempotent).

Issue 3 (cancel robustness) is closed: the cancellation send is wrapped in try/catch and logged, so a WhatsApp+SMS outage no longer throws out before the booking flips CANCELLED, the event is deleted, and reminders are dropped.

Issue 5 (coverage) adds a PAID-reschedule test (no eventId, `updateEvent` skipped, reminders still replaced) and a Calendar-failure-recoverability test; the reminder tests add fire-time match/mismatch cases and remove-then-add replace cases. The assertions pin call ordering and the carried `expectedStartTime`, so they would fail if the fix were reverted.

Issue 6 (unauthenticated routes) is unchanged in behavior and re-stated as an explicit SECURITY/TRUST BOUNDARY comment on both routes — still the one open trust-boundary gap, owned by Phase 6.

### Fire-time backstop now a real run-time guard (issue 1)

The v1 gap was that `sendReminderForBooking` only checked `status === "SCHEDULED"`, which a reschedule preserves, so the comment's promise of a re-time comparison didn't exist in code. It exists now: `enqueueReminders` stamps `expectedStartTime: startTime.toISOString()` into each job's data, `handleSendReminder` parses it back to a `Date` and passes it through, and `sendReminderForBooking` returns `"skipped"` when `expectedStartTime.getTime() !== booking.session.startTime.getTime()`. A stale job that outlived `cancelReminders` for the old slot now skips itself even while the booking is SCHEDULED. The optional parameter leaves any job enqueued before the field existed on status-only behavior — a one-time back-compat window, not a lasting gap.

### Reschedule ordering and recoverability (issues 2 and 4)

The sequence is now: session move (transactional) → `cancelReminders` → `enqueueReminders(newStartTime)` → `updateEvent` → `sendMessage` → clear `lastError`.

```
tx { move session (FOR UPDATE + capacity) }   committed
cancelReminders(old)                           reminders replaced for the NEW time...
enqueueReminders(new)                          ...BEFORE anything fallible below
updateEvent(...)                               throw here => move+reminders already correct, lastError set, 409
sendMessage("reschedule")
booking.update({ lastError: null })
```

This directly fixes issue 2's worst case: a throw in or after reminder replacement can no longer strand a SCHEDULED booking with zero reminders, because replacement is the first thing that runs after the move and both its steps are reminder-queue operations that don't touch Google. For issue 4, a transient `GoogleTransientError`/`GoogleRequestError` from `updateEvent` records `lastError` and rethrows (route → 409) while the DB already reflects the new time and the reminders already target it, so re-running `rescheduleBooking` for the same slot is a session no-op and simply re-patches the event. The deterministic reminder ids plus remove-then-add make the re-driven enqueue idempotent.

The new-ordering trade-off the briefing flagged — reminders enqueued before the event is patched — does not create a wrong-time reminder: the 15m/24h delays are computed from `newStartTime` and `sendMessageForBooking` reads the already-moved `session.startTime` at send time. The only observable lag is the calendar invite sitting at the old window until the patch is re-driven; the booking stays SCHEDULED and the customer-facing message is correct.

`enqueueReminders`'s remove-then-add is what makes the replace real: the ids are keyed on `(kind, bookingId)` only, so without the explicit `getJob`/`remove` a surviving delayed job (carrying the OLD delay and OLD `expectedStartTime`) would make the subsequent `add` a duplicate-id no-op. The past-fire skip is preserved and ordered correctly — the removal happens before the `delay <= 0` check, so a stale job is dropped even when the new reminder is itself skipped (tested by `bk9`). This means a reschedule into a slot less than 15m away still tears down the old jobs rather than leaving them to fire.

### Cancel no longer abortable by a messaging outage (issue 3)

The cancellation send stays before the status flip (the messaging layer only delivers for live statuses), but it is now wrapped in try/catch and logged, so a transient WhatsApp+SMS failure is swallowed and the cancel proceeds to flip CANCELLED, flag captured payments for refund, delete the event, and drop reminders. The messaging layer still records its own failure on the Message row, so the outage isn't lost. The ordering (send → DB transaction → delete event → cancelReminders) is unchanged otherwise, and the terminal-status short-circuit still prevents a second send on an idempotent re-run.

### Test coverage of the fixes (issue 5)

The assertions are tight enough to fail if the fix were reverted: the reschedule test pins `iEnqueue < iUpdate` (reverting the ordering flips it), and the reminder mismatch case goes from `skipped` to `sent` if the fire-time check is dropped. The Calendar-failure test asserts the session moved and reminders were replaced before the injected throw and that `lastError` captured the message.

Coverage gap unchanged: the integration tests are DB-gated (skip without `DATABASE_URL`) and could not run here, and there is still no test for a reschedule-into-a-sub-15m-slot through the full `rescheduleBooking` path — the sub-15m removal is covered at the `enqueueReminders` unit level only. Not blocking.
