# Reminders pipeline, reschedule/cancel, and a minimal messaging substrate (v1)

Phase 5 adds the two session reminders (T-24h, T-15m) as delayed BullMQ jobs with the mandated deterministic ids, a run-time status re-read that skips reminders for bookings that are no longer live, an exponential-backoff retry with alert-on-final-failure, and reschedule/cancel flows that move or tear down the Calendar event plus the reminder jobs. Because Phase 4 left messaging as a stub, the change also builds a minimal messaging substrate (Message table, `lib/messaging.ts` with a WhatsApp→SMS fallback, log-and-succeed provider stubs, and a `send-message` worker) so the reminder path has something to deliver through. Reminders are enqueued only after a booking reaches SCHEDULED, mirroring the existing `createMeetingForBooking` idempotency and Google-error taxonomy. The run-time status check, deterministic ids, and the cancel/reschedule job replacement are the core of the "a rescheduled booking sends only the new reminders" and "forced failure retries then alerts" acceptance criteria.

Watch for: the "only the new reminders" guarantee rests entirely on `cancelReminders` succeeding — the run-time guard checks `status === "SCHEDULED"` but a rescheduled booking stays SCHEDULED, so a stale job that survives cancellation will still fire (likely). The reschedule flow runs the Calendar update, job replacement, and update message as a sequence of independent awaited steps with no transaction or compensation, so a failure midway can leave a SCHEDULED booking with no reminders (likely). `cancelBooking` sends the cancellation message with a direct, un-retried call before the status flip, so a transient send failure aborts the entire cancel (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The reminder scheduling is clean: `enqueueReminders` computes each job's delay from the session start, skips any reminder whose fire time has already passed, and uses exactly the spec's `reminder-24h-<bookingId>` / `reminder-15m-<bookingId>` ids so a reschedule or cancel can look them up. Attempts and exponential backoff match the existing meeting queue.

The run-time skip is where the "only the new reminders" guarantee is weaker than the code comment claims. `sendReminderForBooking` re-reads the booking and skips when the status is not SCHEDULED — correct for cancellation, but a rescheduled booking is still SCHEDULED. The guarantee therefore depends on `cancelReminders` actually removing the old delayed jobs; the run-time check is not a backstop for a reschedule the way the comment ("see a non-SCHEDULED (or re-timed) booking, and quietly skip") asserts, because there is no re-time comparison.

Reschedule performs the session move under the same FOR UPDATE + capacity pattern as `createHold`, inside a transaction. But everything after the move — the Calendar patch, `cancelReminders`, `enqueueReminders`, the update message, and clearing `lastError` — runs as a bare sequence outside any transaction, with no compensation if a middle step throws. The ordering (cancel before enqueue) is right and tested; the atomicity across the whole operation is not.

Cancel marks the booking CANCELLED and flags captured payments for refund in one transaction, deletes the event (treating 404/410 as success), and drops the reminder jobs. It notifies the customer before the status flip because the messaging layer only sends for live statuses — correct intent, but that notification is a direct un-retried call that gates the rest of the cancel.

The final-failure path is wired through the worker's `failed` listener, which fires `reportMessageFailure` only once attempts are exhausted and the error was transient. That marks the Message row FAILED, records `booking.lastError` for the dashboard flag, and alerts the influencer. The reminder failure reuses the same reporting with a `reminder-24h`/`reminder-15m` template.

The reschedule and cancel routes are unauthenticated, documented as deliberate parity with existing routes pending Phase 6 auth.

<summary>Issues (6)</summary>

1. **Reschedule skip not backstopped at run time** — a rescheduled booking stays SCHEDULED, so the run-time guard won't skip a stale reminder; the "only new reminders" outcome depends solely on `cancelReminders` removing the old jobs. Add a run-time check that the reminder's intended fire time still matches the booking's current `session.startTime` (or carry the expected start in job data and compare), so a surviving stale job skips itself.
2. **Reschedule has no atomicity across side effects** — Calendar patch, `cancelReminders`, `enqueueReminders`, update message, and `lastError` clear run as independent awaits; a throw after `cancelReminders` but before/within `enqueueReminders` leaves a SCHEDULED booking with no reminders. Enqueue the new reminders before (or guarantee it runs despite) failures in later steps, or make the message send a queued job so it can't abort reminder replacement.
3. **Cancel aborts if the cancellation message send throws** — `deps.sendMessage(..., "cancellation")` is a direct, un-retried call made before the status flip; a transient provider failure throws and the booking is never marked CANCELLED, the event never deleted, reminders never dropped. Queue the cancellation message (like the confirmation) or move the direct send after the DB flip and tolerate its failure.
4. **Reschedule Calendar patch failure strands the session move** — the session move commits in its own transaction; a later transient/`GoogleRequestError` from `updateEvent` sets `lastError` and throws (route → 409), but the booking already points at the new session with no event update and no reminder replacement, and nothing retries. Consider replacing reminders / recording a recoverable state so the event can be re-patched, or move the booking only after the event patch succeeds.
5. **Reschedule from PAID enqueues reminders while no event exists** — a PAID booking has no `eventId`, so `updateEvent` is skipped but `enqueueReminders` still runs for the new time; harmless (run-time guard skips until SCHEDULED and the deterministic id dedupes the later createMeeting enqueue), but the PAID reschedule path is untested. Add coverage for rescheduling a PAID booking.
6. **Unauthenticated reschedule/cancel routes** — anyone with a booking id can move or cancel a booking and trigger a refund flag. Documented as deliberate pending Phase 6 auth; flagged here as the trust-boundary gap to close before these routes ship.

### Run-time status re-read and the reschedule gap

`sendReminderForBooking` re-reads `{ id, status }` at run time and skips anything not SCHEDULED, which is what makes a cancelled booking's stale reminder a no-op (tested for the cancelled and missing-booking cases). The gap is the reschedule case: a reschedule leaves the booking SCHEDULED and only moves it to a new session, so the run-time guard does **not** catch a stale reminder for the old time — the old jobs are removed by `cancelReminders`, nothing else. The comment in `reminders.ts` claims the stale jobs "run, see a non-SCHEDULED (or re-timed) booking, and quietly skip," but there is no re-time comparison in the code; `status !== "SCHEDULED"` is the only check. If `cancelReminders` misses a job (e.g. the delayed job already promoted to active, a transient Redis error swallowed, or the reschedule throwing between cancel and enqueue), a stale reminder fires. Because `sendMessageForBooking` re-reads `session.startTime`, the message body would carry the new time, but the reminder fires at the *old* schedule — the customer gets a "your session is in 24h/15m" message at the wrong moment. To make the run-time guard a real backstop (as the comment promises), the reminder should compare its intended fire time against the booking's current `session.startTime` and skip on mismatch.

### Reschedule atomicity

```
tx { move session (FOR UPDATE + capacity) }   <-- committed
updateEvent(...)                               <-- throws here => session moved, no reminders replaced
cancelReminders(...)                           <-- throws here => old jobs gone, new not enqueued
enqueueReminders(...)
sendMessage("reschedule")
booking.update({ lastError: null })
```

Only the session move is transactional. Each subsequent step is an independent await with no compensation. The most damaging ordering is a failure in or right after `cancelReminders`: the old reminders are gone and the new ones were never enqueued, so a SCHEDULED booking silently has no reminders at all and nothing re-drives the reschedule. The step ordering itself (updateEvent → cancelReminders → enqueueReminders) is correct and asserted in the test, but the test only exercises the all-success path. Enqueuing the new reminders before dropping the old ones (the deterministic ids make a double-enqueue safe), or making the later steps resilient, would close this.

### Cancel flow and refund flagging

`cancelBooking` short-circuits terminal statuses to `already-cancelled` (no second delete/alert — tested), flags captured payments with `needsRefund = true` and a reason in the same transaction as the status flip, deletes the event after the flip (so a retry still finds CANCELLED and skips), and drops the reminder jobs. The refund is only flagged, with a documented `TODO(phase-6)` for the actual Razorpay movement, consistent with `lib/payment-webhook.ts`.

The customer notification is sent *before* the status flip, because `sendMessageForBooking` only delivers for PAID/SCHEDULED/COMPLETED and would skip after the flip to CANCELLED. The reasoning is sound, but the send is a direct call to `deps.sendMessage` rather than a queued job, and it is awaited before any DB mutation. A transient WhatsApp+SMS failure throws out of `cancelBooking` before the booking is marked CANCELLED, the event is deleted, or the reminders are dropped — the cancel is fully aborted by a messaging hiccup, and the only retry is whatever the caller does. The confirmation message goes through the queue precisely so a provider outage can't block the booking; the cancellation message should get the same treatment, or be sent after the flip and allowed to fail.

### Final-failure report wiring

`reportMessageFailure` flips the Message row to FAILED, writes `booking.lastError` (the dashboard flag), and alerts the influencer with the new `message-delivery-failed` kind. The worker's `failed` listener gates this on `job.attemptsMade >= (job.opts.attempts ?? 1)` and `!(err instanceof UnrecoverableError)`, so it fires exactly once after the last transient attempt. The reminder failure reuses the same report with a `reminder-<kind>` template, so a reminder that exhausts retries lands on the same `(bookingId, template)` Message row the delivery attempts wrote to — the single-row-per-template upsert is what keeps retries from duplicating rows.
