# Group sessions, influencer dashboard, and customer self-service (v1)

Phase 6 adds small-group sessions sharing one Meet event, an influencer dashboard (sessions, earnings, per-booking message status), service/availability/blocked-date management, manual actions (resend/cancel/reschedule), a customer self-service page behind a distinct signed link, and an email-rendering stub. The group path extends `lib/meeting.ts`: a GROUP session derives one deterministic event id from the session, elects a single creator with an atomic `session.updateMany({where:{eventId:null}})` guard, and adds every other paid attendee to the same event. Seat counting is unchanged (`lib/holds.ts` reused as-is), blocked dates are threaded through both `/api/slots` and hold validation, and cancel/reschedule preserve the shared-event invariant. The group-sharing, dashboard-auth, blocked-date, and idempotency work is solid and well-tested.

Watch for: (1) **confirmed** — the booking confirmation/receipt email is never sent on the normal paid→scheduled path; `sendBookingEmail` is only reachable from resend/reschedule, so the self-service link the spec promises in the confirmation email is never delivered, and the `"receipt"` kind is dead code. (2) **confirmed** — `rescheduleBooking` accepts any future timestamp: it checks only for an exact session-time clash and never validates the new time against availability rules, blocked dates, or capacity, so a dashboard/self-service caller can move a booking off-schedule. (3) **confirmed** — the services PATCH route lets an influencer shrink `capacity` below seats already sold and flip a GROUP service to ONE_TO_ONE with no reconciliation.

**Verdict**: NEEDS_CHANGES

## High-level view

The group shared-event design is the heart of the change and it holds up. One event id is derived from the session (`sessionEventId`), creator election is a single atomic DB write, and both the "creator still mid-flight" and "creator crashed" branches converge on the same deterministic event via idempotent insert-then-read. 1:1 keeps its per-booking event id untouched. Seat safety is unchanged because `createHold` still locks the session row `FOR UPDATE` and counts active seats before inserting.

Auth is two distinct signed purposes. Dashboard mutations verify `influencer-dashboard-link` plus an ownership lookup on every target row (403 bad token, 404 not-theirs); self-service verifies `customer-self-service`, whose token carries the booking id in-band so there is no owner to spoof. The purpose string is mixed into the HMAC, and a round-trip test proves a dashboard token cannot be replayed as a self-service token.

Blocked dates are enforced in both read and write paths: `generateSlots`/`isSlotStart` take a pure set of blocked `YYYY-MM-DD` days, and both `/api/slots` and the hold route load the influencer's blocked days and pass them in. The pure day-math is unit-tested.

The known gaps are around the edges of the happy path, not the group core. The confirmation/receipt email is wired as a stub but never actually invoked when a booking is paid and scheduled, so the self-service link never reaches a customer organically. Reschedule moves a booking without re-validating it against the schedule it is supposed to live on. And the service-edit route can retroactively break the capacity invariant it depends on elsewhere.

### One shared event per group session, and how it survives a crash

The group path keys the Calendar event on the session, not the booking: `sessionEventId(sessionId)` is a sha256 hex digest, distinct from the 1:1 `calendarEventId(bookingId)`, and every booking in the session derives the same id. Creator election is a single atomic write — `prisma.session.updateMany({ where: { id, eventId: null }, data: { eventId } })` — and only the booking whose update returns `count > 0` runs `insertEvent`. Everyone else takes the attendee path. Two concurrent payers therefore cannot both insert.

The non-creator branch is the interesting one and it is handled correctly. If `session.meetLink` is already persisted, the attendee reuses it and calls `addAttendee`. If it is still null (creator mid-flight or crashed), the non-creator runs `insertEvent` itself; because the id is deterministic, Google answers 409 and the code reads the existing event, polls for the link, and persists it — so a stuck creator and later attendees reconverge on the same event and link rather than deadlocking. The final `booking.updateMany({ where: { status: "PAID", eventId: null } })` guard means a booking cancelled while Google was being called is left unlinked instead of being resurrected to SCHEDULED.

```
PAID booking ──► session.updateMany(eventId: null → id)
                   │ count>0 (creator)        │ count==0 (joiner)
                   ▼                           ▼
            insertEvent(sessionEventId)   session.meetLink?
            waitForMeetLink               ├ yes → addAttendee + reuse link
            save session.meetLink         └ no  → insertEvent(409→read) + poll + save link
                   └──────────┬───────────────┘
                              ▼
                 booking.updateMany(PAID,eventId:null → SCHEDULED,eventId,meetLink)
```

The free-Gmail 60-minute group cap is handled as a `console.warn` only when `durationMin > 60`; it does not block creation. That matches the spec's "respect the limit" as advisory, but a group service created with `durationMin > 60` will still schedule and the call will be truncated by Google at run time with no customer-facing signal.

### Reschedule does not re-validate the new time against the schedule

`rescheduleBooking` moves the session and patches the event, but its only guards are `newStart <= now` and a lookup for another session already sitting at `newStart`. It never calls `isSlotStart`, never loads blocked dates, and never checks seat capacity at the destination. The UI picks times from `/api/slots` (which does validate), but both API routes accept any `z.iso.datetime()`, so a hand-crafted dashboard or self-service request can move a booking to a blocked day, outside availability rules, or into an unrelated/full session. For a GROUP session this moves the shared event and every attendee, so one customer's self-service reschedule relocates the whole group. The validation that guards the hold path should be reused here before `session.update`.

### Cancel preserves the shared-event invariant

Group cancel removes only the leaving attendee via `removeAttendee` and deletes the event (clearing the session's `eventId`/`meetLink`) only when `remaining === 0`; 1:1 cancel deletes the booking's own event. The DB cancel and the `needsRefund` flag land before the best-effort calendar call, so a Google failure is recorded and alerted rather than blocking the cancel. One asymmetry: cancel flips `needsRefund` but does not itself issue a refund — consistent with the existing webhook behaviour, so out of scope here.

### Earnings and message status

The dashboard computes `seatsFilled` by excluding CANCELLED/FAILED bookings, so a cancelled group seat is freed in the count shown, and it reads only the single latest Message row per booking (`orderBy createdAt desc, take 1`) for status — meaning a later `whatsapp` row can mask an earlier `email` failure on the same booking. Worth confirming the "latest wins" display is intended rather than per-channel status.

### Email is rendered but never sent on the happy path

`lib/email.ts` renders a confirmation or receipt, embeds the signed self-service link, and records an `email` Message row through the same best-effort pattern as `lib/alerts.ts` — delivery is a structured-log stub, which is the intended Phase 4 placeholder. The problem is reachability: `sendBookingEmail` is only called from `resendBookingLink` and the reschedule `renotify`. The paid→scheduled confirmation (`enqueueConfirmation` in `lib/meeting.ts`) records only a `whatsapp` Message row and enqueues; it never calls `sendBookingEmail`. So a customer who simply books and pays never receives the confirmation/receipt email, and therefore never receives the self-service link the spec says the confirmation email carries. The `"receipt"` kind is never passed by any caller. This is the main functional gap against the Phase 6 "Email receipt/confirmation" task and the self-service delivery claim.

### Service management can retroactively break invariants

The services PATCH applies `capacity` and `type` changes with no reconciliation against existing sessions/bookings. Lowering `capacity` below the number of seats already sold on a live group session, or flipping `type` GROUP→ONE_TO_ONE while capacity stays >1, leaves sessions in a state the seat logic assumes cannot happen (the hold path reads the current `service.capacity`, so a shrink makes a previously-valid group look oversold, and a type flip changes which event-id scheme applies to in-flight bookings). The route should reject a capacity below current active seats and guard type changes on services that already have sessions.

### Migrations and tests

The three migrations (`20261010000000_group_shared_event`, `20261011000000_messages`, `20261012000000_blocked_dates`) are hand-written, use snake_case column names matching the schema, carry ascending timestamps after the `20261009000000` baseline, and match the Prisma models (nullable `event_id`/`meet_link` on sessions, the `messages` and `blocked_dates` tables with correct indexes/FKs). A CI run with `prisma migrate diff` would be the place to confirm no drift, since neither `prisma` nor the build can run in this sandbox.

Tests are meaningful where they exist: the earnings and blocked-date suites are pure and would fail on a real regression, and the self-service token suite exercises tamper/expiry/cross-purpose/wrong-key. The group-meeting test proves one insert for the first booking, add-attendee (no second insert, same link) for the second, and the 1:1 per-booking path — these would catch the most important regressions. Not tested: the concurrent-creator race (two simultaneous `updateMany` claims), the "creator crashed, link not yet saved" reconvergence branch (the second booking always sees a saved link in the fakes), group cancel removing the last attendee and clearing the session, and reschedule validation. The reschedule and capacity gaps above are exactly the behaviours no test currently pins.
