# Group sessions, influencer dashboard, and customer self-service (v2)

Second-pass review after the fix round addressing the seven v1 findings. All seven are resolved: the confirmation email now goes out on the normal paid→scheduled path carrying the self-service link (best-effort, cannot fail the create-meeting job); reschedule validates the new time against availability rules + blocked days via a pure `validateRescheduleTime`, with a `RescheduleNotAllowedError` mapped to 409 at both entry points; the reschedule move runs inside a `$transaction` that locks the session `FOR UPDATE` and re-checks seat count against capacity; the service PATCH rejects (409) lowering capacity below live seats and flipping type on services with live bookings; the group re-notify sends one email per attendee and is documented as intended; new tests cover creator-mid-flight reconvergence, concurrent creators, and group-cancel; and the dashboard now shows the latest message status per channel. The group shared-event, oversell-safety, and distinct-signed-link invariants that were sound in v1 are intact.

Watch for: (1) **possible** — the `"receipt"` `EmailKind` still has no caller; the paid path and all re-notify paths pass `"booking-confirmation"`, so `renderEmail`'s receipt branch is dead code. Not a functional gap (the confirmation carries the link and price), but the Phase 6 "receipt" task is satisfied only by the confirmation email. (2) **confirmed, non-blocking** — none of this can be type-checked, migrated, or run in this sandbox (npm registry blocked, empty `node_modules`, missing `proxy-bootstrap.js`); a CI run with install + `tsc` + `prisma migrate diff` + `node --test` is the only place the build, schema drift, and the DB-dependent tests are actually confirmed.

**Verdict**: APPROVED

## High-level view

Issue 1 (confirmation email) is fixed in `lib/meeting.ts`: `enqueueConfirmation` now calls `deps.sendBookingEmail(bookingId, "booking-confirmation")` between recording the WhatsApp row and enqueueing delivery, so every paid→scheduled booking organically receives the self-service link. The dependency is injected through `MeetingDeps` and `sendBookingEmail` swallows its own errors, so a broken email channel records a `failed` Message row rather than failing the create-meeting job.

Issues 2 and 3 (reschedule validation and capacity) are fixed in `lib/manage.ts`. A pure `validateRescheduleTime` mirrors the hold route's gate (future + `isSlotStart` against the influencer's rules + blocked days) and both the dashboard and self-service routes map the new `RescheduleNotAllowedError` to 409. The move itself now runs in a `$transaction` that rejects a time-clash, locks the session row `FOR UPDATE`, and re-checks live seats against capacity before updating — the whole GROUP session moves atomically and a prior capacity shrink cannot slip an oversell through.

Issue 4 (service PATCH) is fixed: the route computes max active seats across the service's sessions with a filtered `_count` and returns 409 when capacity would drop below that, or when the type would change while any session has live bookings.

Issue 5 (group re-notify) is kept and documented: one confirmation email per attendee, because the shared event moved for all of them and each customer needs their own self-service link. That justification is sound.

Issue 6 (tests) is addressed: `tests/group-meeting.test.ts` gained a creator-mid-flight reconvergence case and a concurrent-creators case; `tests/manage.test.ts` covers `validateRescheduleTime` (past / off-rules / blocked / accepted) and group-cancel (remove-only-this-attendee vs delete-and-clear). These assert on observable behaviour and would fail on the matching regression.

Issue 7 (message status) is fixed: `app/dashboard/page.tsx` reduces each booking's messages to the latest row per channel and `Dashboard.tsx` renders one entry per channel, so a queued WhatsApp row can no longer mask a failed email.

No schema change was needed in the fix round — the migration set is unchanged (`20261010`/`20261011`/`20261012`), consistent with the briefing.

### Confirmation email now reaches customers on the paid path

`enqueueConfirmation` in `lib/meeting.ts` records the `whatsapp` row, then calls `deps.sendBookingEmail(bookingId, CONFIRMATION_TEMPLATE)`, then enqueues. It runs on both the fresh `scheduled` outcome and the `already-scheduled` idempotent replay (when `booking.eventId` is set and status is `SCHEDULED`), so a retried create-meeting job re-sends the confirmation — tolerable because the email layer is itself idempotent-ish (it records a fresh Message row each time) and best-effort. `sendBookingEmail` resolves the self-service link via `buildSelfServiceUrl` inside its own try/catch, records an `email` Message row through `createMessage`/`markMessageSent`/`markMessageFailed`, and never throws, so a missing `APP_URL` or a throwing sender degrades to a `failed` row rather than failing the create-meeting job.

The `"receipt"` kind remains unreachable. `renderEmail` renders it, but every caller — the paid path, `resendBookingLink`, and the reschedule `renotify` — passes `"booking-confirmation"`. The confirmation already includes the captured price and the self-service link, so the spec's "email receipt/confirmation" is functionally covered; the receipt branch is just unused code to wire or remove.

### Reschedule now validates the destination and moves atomically

`validateRescheduleTime` is pure (rules + blocked days passed in, `now` injectable) and rejects a non-future time, a time that is not a real `isSlotStart` out of the availability rules, and a real start that lands on a blocked day — the same three gates as the hold route. `rescheduleBooking` loads the influencer's blocked dates in a ±1-day window around the target, runs the validator, and throws `RescheduleNotAllowedError` on failure; both `app/api/dashboard/bookings/[id]/route.ts` and `app/api/manage/[token]/route.ts` map that error (alongside `BookingNotManageableError`) to 409. The off-schedule / blocked-day / crafted-request hole from v1 is closed at both entry points.

The move itself is now serialized:

```
$transaction:
  findFirst(service_id, start_time = newStart, id != session)  → clash? 409
  SELECT id FROM sessions WHERE id = session FOR UPDATE          (lock, mirrors lib/holds.ts)
  count(active seats on session)  taken > capacity?            → 409
  session.update(startTime, endTime)
```

The `taken > service.capacity` direction is correct here (not the hold path's `>=`): a GROUP reschedule moves the existing session as a unit, so the live-seat count already includes this booking and no new seat is consumed — the guard only fires when a prior capacity shrink left the session already over the new limit. The unique `(service_id, start_time)` constraint plus the explicit clash check prevent merging into a different session at the destination, so the v1 "silently merge into an unrelated session" concern does not apply: the move keeps the same session row and the one-event-per-session invariant.

### Service PATCH guards the capacity invariant it depends on elsewhere

The PATCH route detects `changingType` and `loweringCapacity` against the existing row, and only then queries the service's sessions with a filtered `_count` of bookings matching `activeSeatWhere(now)`. It rejects (409) a type change when any session has live bookings, and a capacity below the max live-seat count across sessions. Because the count uses the same `activeSeatWhere` predicate the hold and reschedule paths use, the guard matches the exact definition of "seats already sold" and is not bypassable through hold/expiry edge cases. The hold path and the shared-group-event path both read the current `service.capacity`/`type`, so this closes the v1 retroactive-invariant break.

### Tests pin the previously-uncovered branches

`tests/group-meeting.test.ts` adds the two branches v1 flagged as untested. The creator-mid-flight case seeds `session.eventId` set but `session.meetLink` null and a Google fake whose `insertEvent` answers `"exists"` for the claimed id; it asserts the non-creator inserts on the deterministic id (409→read), persists the recovered link on the session, and ends SCHEDULED — exercising the reconvergence path that previously always saw a saved link. The concurrent-creators case runs two paid bookings through the atomic `session.updateMany` null-guard and asserts exactly one insert and one add-attendee with a shared link/event id. `tests/manage.test.ts` covers `validateRescheduleTime` across past / off-rules / blocked / accepted, and group-cancel in both shapes: remove-only-this-attendee keeps the shared event (`deleted` empty, session fields retained), and last-attendee-leaves deletes the event and clears `eventId`/`meetLink`. These assert on recorded side effects (`inserts`, `adds`, `removed`, `deleted`, persisted fields) and would fail on the matching regression rather than passing vacuously. As the test headers note, both suites import through the `@/*` alias and `node_modules`, so they run in CI, not the offline sandbox; the pure id-derivation and `validateRescheduleTime` checks are the only parts that run anywhere.

### Dashboard message status is per-channel

`app/dashboard/page.tsx` loads the 20 most recent messages per booking newest-first and reduces them to the first row seen per channel (`latestPerChannel`), and `Dashboard.tsx`'s `messagesLabel` renders one `template · channel · status` entry per channel. A later `queued` whatsapp row therefore no longer hides an earlier `failed` email row on the same booking. `seatsFilled` still excludes CANCELLED/FAILED, so a cancelled group seat is freed in the displayed count.

### Invariants intact from v1

The group shared-event core is unchanged: `sessionEventId` keys the event on the session, creator election is the atomic `session.updateMany({where:{eventId:null}})`, non-creators reuse a saved link or reconverge via idempotent insert-then-read, 1:1 keeps its per-booking `calendarEventId`, and the final `booking.updateMany({status:"PAID",eventId:null})` guard still prevents resurrecting a booking cancelled mid-call. Oversell safety still rests on `createHold`'s `FOR UPDATE` seat count. The two signed-link purposes remain distinct and non-replayable: `influencer-dashboard-link` (carries influencer id, gated by an ownership lookup on every target row) vs `customer-self-service` (carries the booking id in-band, no owner to spoof), each mixed into the HMAC.

### Sandbox limits on what this review could confirm

Nothing here was type-checked, migrated, or executed: the npm registry is blocked, `node_modules` are empty placeholders (no `tsc`/`prisma`/`tsx`/`next`), and `NODE_OPTIONS` preloads a missing `proxy-bootstrap.js`. The review is by reading code. A CI run with `npm install` + `tsc --noEmit` + `prisma migrate diff` (to confirm no schema drift, since the fix round reports no new migration) + `node --test` (to actually run the group-meeting and manage suites that depend on the alias + deps) is where these would be confirmed.
