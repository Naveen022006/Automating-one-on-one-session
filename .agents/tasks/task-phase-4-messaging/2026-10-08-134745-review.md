# WhatsApp + SMS messaging review-fix pass (v2)

The follow-up commit `bdfd83c` resolves all five issues from the v1 review of the Phase 4 messaging pipeline. The WhatsApp POST webhook now verifies Meta's `X-Hub-Signature-256` over the raw body in constant time and returns 401 before any DB write; the verify-token handshake uses a length-checked `timingSafeEqual`; the public status endpoint gates `meetLink` to terminal paid statuses; the `attempts:5` retry budget vs. the Phase 3 gap is documented as a deliberate trade-off; and the delivery-status parser now omits `error` on non-FAILED transitions so a later DELIVERED/READ callback can't wipe a prior FAILED's diagnostic context. The fix commit touched only the files it needed and left the send-flow (`lib/messaging.ts`) and worker untouched, so there is no regression surface outside the five fixes.

Watch for: nothing blocking. One residual behavioral note carried from v1 — the retryable-missing-link path still records no `messages` row while waiting, so "waiting for link" visibility lives only in the BullMQ job state (confirmed, unchanged, and acceptable until Phase 3).

**Verdict**: APPROVED

## High-level view

The signature check is now the first thing the POST handler does after reading the raw body: it rejects with 401 on a missing/malformed/mismatched signature before `JSON.parse`, before `parseWhatsAppStatuses`, and before any `updateMany`. The helper mirrors `verifyWebhookSignature` in `lib/payments.ts` — strips the `sha256=` prefix, hex-decodes defensively, length-checks, then `timingSafeEqual` — so the WhatsApp callback now enforces the same trust boundary the payment webhook does. The GET handshake is unchanged in behavior (still echoes `hub.challenge` on a token match) but the comparison underneath it is now constant-time via a length-checked `safeEqual`.

The `meetLink` field on `/api/bookings/[id]` is gated by a `LINK_VISIBLE_STATUSES` set (`PAID`/`SCHEDULED`/`COMPLETED`); any other status returns `meetLink: null`. Since `meetLink` is only populated post-PAID anyway, a guessed pre-payment id yields nothing, and the rationale (public endpoint, no auth system, cuid ids, link also sent over WhatsApp/SMS) is documented inline and in `doc/04-messaging.md`.

The error-clobber fix is split cleanly across the parser and the route: `parseWhatsAppStatuses` includes the `error` key only on FAILED updates, and the route branches on `"error" in u` to decide whether to write the `error` column at all. A DELIVERED/READ callback therefore updates only `status` and leaves a prior FAILED error intact, consistent with treating provider status as the source of truth.

The retry budget is unchanged (`attempts:5`, exponential backoff 5000, `removeOnFail:false`) and now carries a comment explaining that a bridge job enqueued directly on PAID will exhaust its attempts and land failed-for-inspection until Phase 3's create-meeting job becomes the real producer that sets `meetLink` before enqueueing. This is a documented decision, not a defect.

### Signature verification short-circuits before any state change

The 401 gate sits before every state-touching step — `JSON.parse`, `parseWhatsAppStatuses`, the `updateMany` loop are all inside the `try` block *after* the `verifyMetaSignature` call — so an unauthenticated caller can no longer flip a message status by guessing a `providerMessageId`. The helper rejects a null header, a missing secret, a header without the `sha256=` prefix, a non-hex/wrong-length digest (`Buffer.from(hex, "hex")` + length check), and a correct-length-but-wrong digest via `timingSafeEqual`; the test matrix pins each case including tampered-body and wrong-secret.

One residual edge (not a defect): a malformed JSON body that *passes* signature verification falls into the `catch` and returns 500, which asks Meta to retry. This only affects genuinely corrupt-but-signed bodies, and retrying is a defensible choice.

### meetLink gating closes the capability leak

The gate is `LINK_VISIBLE_STATUSES.has(booking.status) ? booking.meetLink : null`, applied after the DB read. Since `meetLink` is only written post-PAID, this is defense-in-depth: a non-terminal booking never returns a link even if one were somehow present, and a pre-payment guessed id yields nothing. The deferred session/ownership check is documented rather than papered over, which is the right call given there is no auth system yet.

### Error preservation across out-of-order callbacks

`parseWhatsAppStatuses` emits `{ providerMessageId, status, error }` only for FAILED (error = first provider message/title/code), and `{ providerMessageId, status }` otherwise. The route's `"error" in u ? { status, error } : { status }` means a DELIVERED/READ `updateMany` writes only the `status` column, so a prior FAILED's stored error survives an out-of-order or failed→delivered transition. This is now pinned by a test asserting `"error" in u === false` on a non-FAILED update.

### Retry budget documented, not changed

`enqueueSendMessage` mirrors `enqueueCreateMeeting` (deterministic `jobId`, `attempts:5`, exponential backoff 5000, `removeOnFail:false`). The documented bridge lifecycle: in the current repo state a send-message job enqueued on PAID retries while `meetLink` is null, exhausts five attempts over a few minutes, and lands failed-for-inspection; once Phase 3 lands, create-meeting sets the link and owns enqueueing send-message after it exists. Not inflating the budget for the bridge window is the right call — a higher budget would only mask the absent Phase 3 producer. The bridge in `payment-webhook.ts` enqueues both jobs inside the captured path, injectable for offline tests.

### Residual visibility note from v1 (unchanged, non-blocking)

The retryable-missing-link path in `sendBookingMessage` still throws before recording any `messages` row, so a booking waiting on a link leaves no DB trace — operational visibility depends on the queue. This was flagged in v1 as an observation, not a required fix, and remains acceptable for the bridge window.

### Tests

The new tests in `tests/whatsapp-webhook.test.ts` cover the signature accept path, the reject matrix (tampered body, wrong secret, null header, missing secret, missing prefix, non-hex digest), the constant-time wrong-length verify-token reject, and the error-omitted-on-non-FAILED behavior — exactly the branches the fixes introduced, in the `tests/signature.test.ts` style.

Not tested: the same route-level gap noted in v1 — no end-to-end test asserts the POST handler returns 401 on a bad signature before `updateMany`, since the repo tests pure helpers over route handlers. Helper-level coverage still makes a regression on the signature logic itself detectable, so the gap is low-risk.

### Unrelated changes

None. The fix commit touches only the five concern areas plus the v1 review file (bookkeeping), the FEAT-002 task-state JSON, the `.env.example` secret, and the doc. No scope creep.
