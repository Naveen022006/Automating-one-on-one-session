# WhatsApp + SMS messaging for paid bookings (v1)

Phase 4 adds the messaging pipeline that delivers the meeting link to a paid booking: WhatsApp first, SMS as fallback, with every attempt recorded in a new `messages` table and a delivery-status webhook that advances rows from SENT to DELIVERED/READ/FAILED. Because Phase 3 (Google Meet) does not exist in this repo, the implementer added `Booking.meetLink`/`eventId` now, wired `payment-webhook` to enqueue the send-message job directly on PAID, and made `sendBookingMessage` throw a retryable error while `meetLink` is null so BullMQ keeps retrying until a link appears. The queue layer was refactored from a single lazy queue to a `Map` of named queues, and a BullMQ worker consumes the new `messages` queue (guarded when `REDIS_URL` is unset). The cross-phase bridge is deliberate and documented in code and in `doc/04-messaging.md`.

Watch for: the WhatsApp POST webhook accepts and acts on unauthenticated callbacks — no `X-Hub-Signature-256` verification, unlike the payment webhook's HMAC check (confirmed). The verify-token handshake compares with `===` rather than a constant-time compare the repo already has on hand (likely). Adding `meetLink` to the unauthenticated `/api/bookings/[id]` endpoint turns a guessable booking id into a meeting-join capability (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The send flow handles the opt-out skip and the retryable-missing-link path before any provider call, then records a PENDING row per attempt and falls back WhatsApp→SMS. The unit tests exercise each branch against an in-memory fake and would fail if the ordering or gates were reverted.

The delivery-status webhook is where the security posture diverges from the rest of the codebase. The payment webhook verifies an HMAC signature over the raw body in constant time before trusting anything; the WhatsApp POST handler reads the body and immediately applies status updates keyed by `providerMessageId` with no signature check at all. Meta signs these callbacks with `X-Hub-Signature-256` using the app secret, and the raw body is already read in the right place to verify it. As written, anyone who can reach the endpoint and guess/observe a provider message id can flip a message's status (including to FAILED). The GET verify handshake is gated correctly on a matching token but uses a plain `===` comparison where the project otherwise uses `timingSafeEqual`.

The queue refactor to a name-keyed `Map` preserves the original job options (attempts 5, exponential backoff 5000, deterministic jobId, removeOnFail false) and extends them to the message queue, so retry/idempotency semantics are consistent across both queues. The cross-phase bridge enqueues send-message alongside create-meeting inside the same PAID transaction path, and the retryable-error-until-meetLink design means those jobs will spin through retries indefinitely in this repo state — acceptable and documented, but worth remembering that with `attempts: 5` the job will exhaust retries and land in a failed state long before a (nonexistent) Phase 3 job could set the link.

The confirmation UI and status endpoint now surface `meetLink` so a messaging failure never blocks the customer, which satisfies the doc rule. The tradeoff is that the status endpoint is unauthenticated and now returns the join link.

### Send flow, attempt recording, and the opt-out / missing-link gates

`sendBookingMessage` reads exactly the four fields it needs, returns `{ channel: null, skipped: true }` for opted-out or missing-number bookings without recording a row, and throws `RetryableMessageError` when `meetLink` is null before any provider call or DB write. Only after those gates does it create a PENDING WhatsApp row, promote it to SENT with the provider id on success, or mark it FAILED and create a second PENDING SMS row for the fallback. When both channels fail it marks the SMS row FAILED and throws a plain `Error`, so BullMQ retries the whole job.

One asymmetry: the retryable path throws *before* recording anything, so a booking stuck without a `meetLink` leaves no trace in `messages` across its retry lifetime — the only signal is the BullMQ job state. Operational visibility into "waiting for link" bookings depends entirely on the queue, not the DB.

### WhatsApp delivery-status webhook: trust boundary

```
Meta  --POST (X-Hub-Signature-256)-->  /api/webhooks/whatsapp  -->  message.updateMany(by providerMessageId)
                                        ^ no signature check
```

The payment webhook establishes the repo's contract for provider callbacks: read raw body, verify HMAC in constant time, reject on mismatch, then process. The WhatsApp POST handler reads the raw body (good — needed for signature verification) but parses and applies status updates with no verification. Meta provides `X-Hub-Signature-256` precisely for this. Because updates are keyed on `providerMessageId` and applied with `updateMany`, an unauthenticated caller who learns or guesses a provider id can mark a real message FAILED (or READ). The verification primitives already exist in `lib/payments.ts`.

### meetLink on the public status endpoint

`/api/bookings/[id]` is explicitly a public, unauthenticated poll ("the browser never decides that a payment succeeded"). Previously it leaked only `status` and `holdExpiresAt`; this PR adds `meetLink`. A Google Meet join link is a capability — possession grants entry — so returning it to anyone who can enumerate or guess a booking cuid widens the exposure. cuids are not trivially guessable, which keeps this below critical, but the link is longer-lived and higher-value than a status flag. Gating the field behind an ownership/session check, or delivering the link only via the messaging channels + confirmation screen tied to the active session, would close it.

### Error field overwrite on later status callbacks

`parseWhatsAppStatuses` sets `error` to the first provider error only when the mapped status is FAILED, and to `null` otherwise. Delivery callbacks can arrive out of order or a message can transition failed→retried→delivered at the provider; a subsequent DELIVERED/READ update will null out an error that a prior FAILED stored. If `status` is treated as the single source of truth this is fine, but it silently discards diagnostic context. Worth a conscious decision rather than a side effect of the mapping.

### Tests

`tests/messaging.test.ts` covers the five meaningful branches — WhatsApp success, WhatsApp-fail→SMS-success, opt-out skip, missing-link retryable throw, both-fail throw — against an in-memory prisma fake, asserting both the returned channel and the recorded row states. These would fail if the fallback ordering, the skip gate, or the retryable path were reverted. `tests/whatsapp-webhook.test.ts` exercises the pure helpers: status mapping including the unknown→null case, the verify-token accept/reject matrix (wrong token, wrong mode, undefined expected, all-null), and the status flattener including malformed payloads and the keep-error-on-failed behavior. `tests/payments.test.ts` was updated to assert the bridge enqueues exactly one send-message per paid booking and that the duplicate/rollback paths still hold.

Not tested: the POST route handler itself (no coverage that a signature check exists or that `updateMany` is called with the parsed updates) — which is also why the missing signature verification isn't caught by a test. No test asserts that an unknown `providerMessageId` is a safe no-op end to end. These are route-level gaps, consistent with the repo's pattern of testing pure logic over route handlers, but the missing-signature issue would ideally be pinned by a test once added.

### Unrelated changes

None bundled. The `.agents/tasks/...` JSON files are task-state bookkeeping, and the doc checkbox updates and `.env.example` additions all belong to this phase.
